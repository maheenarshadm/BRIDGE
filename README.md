# BRIDGE

BRIDGE is a business rule-guided approach for automated test data generation
for data-intensive systems. It takes business rules modeled as DMN decision
tables, together with the relational database schema of a system, and
generates database states that exercise the business rules while remaining
consistent with the schema.

This repository contains the implementation of BRIDGE, the case-study inputs,
the scripts of the evaluation, and the result tables and numbers reported in
the paper.

## Approach

BRIDGE works in three phases.

1. **DMN grounding and objective construction** (`bridge/grounding`). Every
   rule of a FIRST or UNIQUE decision table becomes a search objective. Every
   decision input is resolved against the schema: a column, a null check, an
   aggregate over related rows, the existence of related rows, a value reached
   through a join, the output of an upstream decision, or a value that is not
   stored in the database. The hit-policy context of a rule records the
   preceding rules that must not match.
2. **Schema-aware evolutionary search** (`bridge/search`). A many-objective
   search based on DynaMOSA evolves whole database states. The fitness of an
   objective combines the branch distance of the rule's condition with the
   distance to falsify the preceding rules. Objectives whose upstream
   prerequisites are not yet satisfied are kept out of the search until they
   become reachable, and a schema repair keeps every candidate consistent
   with keys, foreign keys and NOT NULL constraints.
3. **Dataset construction and validation** (`bridge/construction`,
   `bridge/validation`, `bridge/minimization.py`). The individuals found by
   the search are built into SQLite databases and validated by an independent
   validator that re-executes the DMN decisions against each database. A rule
   counts as covered only if a database makes its decision select it. The
   smallest set of databases that together verify every covered rule forms
   the final test suite.

## Case studies

The evaluation uses four subject systems: one industrial system, FLEX2, and
three open-source systems, jBilling, OpenMRS and Spree. Due to proprietary
restrictions, the business rules, database schema and test data of FLEX2
cannot be shared. This repository therefore includes the inputs and results
of jBilling, OpenMRS and Spree.

| Case study | System | Decision tables | Rules | Tables in schema |
|---|---|---|---|---|
| C02 | jBilling, billing and invoicing | 10 | 20 | 98 |
| C03 | OpenMRS, medical records | 17 | 55 | 119 |
| C04 | Spree, e-commerce | 7 | 22 | 197 |

Each case study is described by the files in `case_studies/<name>/`:

| File | Content |
|---|---|
| `dmn/*.dmn` | DMN decision models of the business rules |
| `grounding.csv` | Mapping of every decision input to its source in the schema (column, aggregate, existence check, join, or not stored in the database) |
| `schema.json` | Relational schema: primary keys, columns with types and NOT NULL flags, foreign keys, unique indexes, check constraints |
| `not_persisted*.json` | Fixed values of decision inputs that are not stored in the database, used during validation (one file per validation setting) |
| `config.json` | Column names of `grounding.csv`, the validation settings, and the objectives used in the evaluation |

The schema files were extracted from the systems' SQL schema (jBilling),
Liquibase changelogs (OpenMRS) and Rails migrations (Spree).
`case_studies/compiled_constraints.json` holds the compiled search objectives
of the three case studies and is regenerated by `python -m bridge compile`.

## Repository structure

```
bridge/              the approach
  grounding/         phase 1: DMN parsing, grounding and objective construction
  search/            phase 2: chromosome, fitness, mutation, crossover, DynaMOSA
  construction/      phase 3: building SQLite databases from individuals
  validation/        phase 3: independent validator
  minimization.py    exact minimal test suite
  pipeline.py        the approach end to end for one case study
case_studies/        inputs of jBilling, OpenMRS and Spree
evaluation/          experiments and analyses of the paper
  experiment.py      repeated runs of BRIDGE, GM and GS with equal budgets
  baselines/         GM, GS and SR
  merge.py           combining runs executed on several machines
  statistics.py      normality tests, comparison tests, effect sizes
  paper_tables.py    tables, figure data and numbers
  configs/paper.json base budget B of every case study
results/             tables and numbers reported in the paper
tests/               unit tests, pipeline tests and a reproduction check
reproduce.py         regenerates results/ from experiment runs
```

## Requirements

Python 3.13 or later and PyYAML. The experiments were run with Python 3.13
and 3.14. No GPU, network access or external service is needed.

```
python -m venv .venv
source .venv/bin/activate          (Windows: .venv\Scripts\activate)
pip install -r requirements.txt
```

All commands are run from the repository root.

## Running BRIDGE

Generate the test databases of one case study with a budget of fitness
evaluations (here the base budget of jBilling):

```
python -m bridge generate --case-study jBilling --budget 78970 --seed 0
```

The output folder (`outputs/jbilling_seed0/` by default) contains:

- `minimal_suite/database_NN.db`: the test databases (SQLite),
- `coverage.json`: the rules each test database verifies,
- `summary.json`: the number of rules verified, the size of the minimal
  suite and the rules that were not verified.

To recompile the search objectives from the DMN models:

```
python -m bridge compile
```

## Reproducing the evaluation

The evaluation compares BRIDGE with three baselines at equal budgets of
fitness evaluations.

| Technique | Setup name in the outputs | Description |
|---|---|---|
| BRIDGE | `dynamosa` | the approach |
| GM | `random_walk` | grounded mutation: random mutation of the grounded inputs, without fitness guidance |
| GS | `random_sample` | grounded sampling: independent random assignments of the grounded inputs |
| SR | `schema_random` | random databases generated from the schema alone, checked by the validator |

Every configuration is repeated 30 times with budgets of 1B, 5B and 10B,
where B is the base budget of the case study in `evaluation/configs/paper.json`
(jBilling 78,970, OpenMRS 207,920 and Spree 86,297 fitness evaluations). Run
r with budget kB uses the seed 1000k + r.

1. Run BRIDGE, GM and GS:

   ```
   python -m evaluation.experiment run --name paper --reps 30
   ```

   Runs are written to `outputs/paper__from_rep00/`. To share the work among
   machines, give each machine a range of repetitions with `--first-rep` and
   `--reps`, copy the output folders together and combine them with
   `python -m evaluation.merge --name paper --into paper`.

2. Run SR:

   ```
   python -m evaluation.baselines.schema_random run --name paper --reps 30
   ```

3. Summarize the runs and regenerate the tables and numbers:

   ```
   python -m evaluation.experiment summarize --name paper__from_rep00
   python reproduce.py --results outputs/paper__from_rep00 --schema-random outputs/paper_schemarandom__from_rep00
   ```

Every run executes in its own process with `PYTHONHASHSEED=0` and fixed
seeds, so runs are reproducible. In the paper's experiments, the median
search time of one run of BRIDGE was 0.1 to 0.2 minutes with budget 1B and 1
to 2.4 minutes with budget 10B, depending on the case study. Validation adds
to this, and the experiment runs four jobs in parallel by default. `python -m evaluation.experiment calibrate --name NAME`
recomputes the base budgets.

## Results

`results/` contains the tables and numbers of the evaluation for jBilling,
OpenMRS and Spree, generated by `reproduce.py` from the runs of the paper.

| File | Content |
|---|---|
| `tables/tab_rq1_coverage.tex` | Mean verified rule coverage per budget (RQ1, RQ2) |
| `tables/tab_rq1_stats.tex` | Vargha-Delaney A12 of BRIDGE against each baseline (RQ1, RQ2) |
| `tables/tab_rq1_rules.tex` | Non-trivial and unreached rules (RQ1) |
| `tables/tab_runs_1B.tex`, `tab_runs_5B.tex`, `tab_runs_10B.tex` | Verified coverage of every run (RQ1) |
| `tables/fig_coverage.tex` | Coverage during the base budget (RQ2) |
| `tables/tab_rq3_suite.tex` | Minimal test suites of the outputs of BRIDGE (RQ3) |
| `tables/tab_rq3_same.tex` | Suite sizes of BRIDGE and each baseline for the same rules (RQ3) |
| `numbers/results.json` | Every number of the analysis |
| `numbers/per_run.csv` | Verified coverage and minimal suite sizes of every run |
| `statistics/normality.csv` | Shapiro-Wilk test of every sample |
| `statistics/comparisons.csv` | Comparisons of BRIDGE with each baseline |
| `statistics/paired.csv` | Comparisons of the archive and the final population |

The statistical tests are chosen per comparison: Welch's t-test when both
samples pass the Shapiro-Wilk test and the Mann-Whitney U test otherwise, and
the paired t-test or the Wilcoxon signed-rank test for paired samples. The
effect size is the Vargha-Delaney A12 statistic, and p-values are adjusted
with the Holm correction.
